# Gate G-WB: calibrate the Shadow Runtime against a licensed Workbench

Status: `WAITING_ON_HUMAN`

## Why a human is needed

The Niagara Shadow Runtime (milestone N6) is a model of how Niagara executes a
`.bog`. Every behavior it assumes is listed in `docs/niagara-semantics.md` with a
source. Assumptions marked `ASSUMED` can only be confirmed by running the same file in
a real Niagara station, which needs a licensed Workbench. Until this gate passes,
every result the Shadow Runtime produces is labelled `bog-simulated`, below
`runtime-qualified`.

## What you need

- A licensed Niagara 4 Workbench with a localhost station (a JACE or Edge device is
  better but not required for the first pass).
- The signed `bactalkG36` module from Gate G-SDK installed in that Workbench.
- About two hours.

## Steps

1. Check out the repository at the commit named in `STATUS.md` under N7.
2. Open `calibration/README.md`. It lists one folder per ASSUMED rule (17 folders
   covering all 24 ASSUMED rows; `docs/niagara-semantics.md` names which rule each
   folder also covers), in the order to run them, and for each one the exact operator
   steps with their times and the histories to export. The kit is generated by
   `scripts/build_calibration_kit.py` and checked against the code by
   `tests/test_native_bog_calibration.py`, so it is never stale.
3. For each folder: import `program.bog` into the station, note the wall-clock moment
   you start it (t = 0), apply the `steps.json` actions at the listed times
   (`override` at level 8 with the listed value, `auto` to remove the override) using
   the writable points under `Inputs`, wait `duration_seconds`, then export each history
   under `Outputs/<point>/<point>History` as CSV to
   `gates/evidence/G-WB/<folder>/<point>.csv` (for example
   `gates/evidence/G-WB/s-status-4/sum.csv`). Any export with a timestamp column and a
   value column is accepted; a status column is used when present.
4. Run `python scripts/calibrate_shadow_runtime.py gates/evidence/G-WB`. It aligns
   each export's clock to the expected trace, compares every record with
   `expected-<point>.csv` (1.5 s timing tolerance, 0.1 % value tolerance), prints a
   verdict per rule and rewrites the status cell of each rule in
   `docs/niagara-semantics.md` to `… → VERIFIED (G-WB <date>)` or
   `… → CONTRADICTED (G-WB <date>)`. Two rules (S-LINK-4, S-CLOCK-1) record the
   station's ordering either way; a mismatch there is still evidence, not a defect.
5. Import each Tier 1 exported `.bog` (create the demo runs with
   `POST /api/runs/demo` and `POST /api/runs/demo/generalist`, or run
   `scripts/native_bog_proofs.py --only d1`, and take the `.bog` from the run
   directory) into the station and confirm it opens with no errors in the Workbench
   console, that every folder renders, and that no link is broken. Record the outcome
   in `gates/evidence/G-WB/imports.md`.

## Evidence to return

- The exported history CSVs, one directory per assumption.
- `imports.md` with the Workbench version and any console messages.
- The updated `docs/niagara-semantics.md` (the script edits it) in the same commit.

## What passing means

Every assumption reads `VERIFIED`, or every `CONTRADICTED` assumption has a failing
test opened against the Shadow Runtime and a fix committed before the next release.
Passing this gate moves evidence produced by the Shadow Runtime from `bog-simulated`
toward `runtime-qualified`. It still does not mean field qualification; that is a
commissioning activity on the actual equipment.
